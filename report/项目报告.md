## 1. Objectives and architecture

The system provides flight information, reservations and time-limited seat monitoring over IPv4 UDP. It also implements an idempotent fare-setting operation and a non-idempotent fare-increase operation. A Java server interoperates with Python clients through an explicit binary protocol. The production system uses only the JDK and Python standard library; it does not use RMI, RPC frameworks, CORBA, Java object serialization or stream-based network marshalling.

The client menu and experiment driver call the same Invoker. The Invoker allocates a session/request identity, encodes the request once and uses one UDP socket for requests, replies and callbacks. The server receives a datagram, validates it, applies the selected invocation semantics and delegates business work to DefaultFlightService. That service shares one InMemoryMonitorService with the dispatcher. Business code returns typed responses and callback events rather than sending packets itself.

The server uses a sequential receive/dispatch loop. This makes history lookup, business execution and result recording ordered without a thread per request. A 250 ms receive timeout permits subscription cleanup while idle. The shutdown hook closes the socket to unblock reception. Business data, subscriptions and duplicate history are in memory and reset on restart.

Part A implements BinaryProtocolCodec, UdpTransport, UdpServer, RequestDispatcher, InMemoryRequestHistory, LossSimulator and structured ServerLog output. The shared business and client interfaces isolate protocol/transport work from flight-state changes and user interaction. Protocol errors retain sufficient local metadata to encode a safe error reply without changing the agreed wire format.

## 2. Explicit binary protocol

All multi-byte numbers use network byte order. Signed integers occupy four bytes; fares use IEEE 754 binary32. Locations and error text use strict UTF-8, prefixed by a four-byte byte count rather than a character count. Java manually shifts integer/UUID bytes and converts float bits; it does not serialize objects or use input/output streams to marshal messages. Python follows the same field layout. Dates contain five integers: year, month, day, hour and minute, interpreted in UTC+8.

| Header field | Bytes | Meaning |
|---|---:|---|
| version | 1 | Protocol version 1 |
| messageType | 1 | Request 1, reply 2, callback 3 |
| operation | 2 | Operations 1 through 6 |
| sessionId | 16 | Nonzero UUID |
| requestId | 4 | Positive signed integer |
| status | 2 | Success 0 or defined error 1 through 9 |
| semantics | 1 | ALO 1 or AMO 2 |
| reserved | 1 | Must be zero |
| bodyLength | 4 | Exact bytes following the header |

The header is exactly 32 bytes. The application maximum is 1024 bytes, while reception uses a 65535-byte buffer to detect oversized UDP messages rather than silently truncating them to the application limit. Decoding uses the actual packet offset and length. It rejects missing fields, extra bytes, negative lengths, malformed UTF-8, invalid response dates and non-finite response fares. Location text is limited to 128 encoded bytes and error text to 256 bytes. Typed but business-invalid request values are passed to business validation and receive a normal business error.

Malformed packets with a trustworthy request identity receive a protocol error; identities that cannot safely be recovered are silently dropped. Oversized messages return status 9 when identity is trustworthy. Unsupported operations return 6; mode mismatch returns 7 and echoes the requested mode so the client can match the error. Malformed-message status is 5 and conflicting reuse of an AMO request key is 8. These pre-business failures do not populate business history.

The repository's protocol specification v1.0 defines the normative byte layout, status definitions and fixed vectors. Java-to-Python and Python-to-Java vector tests cover requests, successful responses, errors and callbacks, including Chinese UTF-8 locations.

## 3. Flight operations and business state

| Operation | Request body | Successful response body |
|---|---|---|
| QUERY_ROUTE (1) | Source and destination strings | Count followed by all matching flight IDs |
| QUERY_FLIGHT (2) | Flight ID | Five departure-time integers, fare, available seats |
| RESERVE_SEATS (3) | Flight ID, quantity | Flight ID, remaining seats |
| MONITOR (4) | Flight ID, duration in seconds | Flight ID, remaining milliseconds |
| SET_AIRFARE (5) | Flight ID, new fare | Flight ID, resulting fare |
| INCREASE_AIRFARE (6) | Flight ID, positive increment | Flight ID, resulting fare |

Route results are sorted and include all matches. Detail responses deliberately do not repeat the flight ID: clients already have the request context, and both implementations follow the agreed response shape. Reservation validation completes before state changes; invalid quantities, unknown flights and insufficient seats produce errors with no seat or sequence-number side effects.

The six-flight seed includes two Singapore-to-Beijing matches, a sold-out Singapore-to-Shanghai flight, Chinese-location routes and a reverse route. Flight 1001 starts with 10 seats, fare 100 and update sequence 0. Each experiment starts a fresh server and session to restore this known state. The controlled reservation quantity is 1, SET fare is 120 and INCREASE delta is 20.

SET_AIRFARE is idempotent with respect to fare state: applying the same assignment twice leaves the same value. INCREASE_AIRFARE is non-idempotent: two successful additions of 20 change 100 to 140. Reserving seats is also non-idempotent. Business validation rejects non-finite, out-of-range and ineffective floating-point changes as required by the shared specification. Fare changes do not generate seat-change callbacks.

## 4. Retries and invocation semantics

A client creates a fresh UUID session and increasing positive request IDs. A logical call is encoded once. Every retry retains identical bytes, UUID, request ID and source socket. Defaults are a 1000 ms timeout and five total attempts, including the initial send. Irrelevant, malformed or late messages do not extend an attempt's absolute deadline. Replies must match the configured server endpoint and outstanding request identity, operation and semantics.

In ALO mode, the server executes every valid received request, including duplicates. Retries improve the chance of completion, but a finite retry budget does not guarantee delivery when all requests are lost. A lost reply may cause a non-idempotent operation to execute multiple times.

In AMO mode, the server first checks history keyed by (session UUID, request ID). An entry retains the original request bytes, peer endpoint and immutable result. Matching duplicates replay the result without invoking the business method again. Reuse with different bytes or a different peer is rejected. Successes and business errors are saved before ordinary reply transmission or simulated reply loss. Thus a retry after a lost business error receives the same error even if other clients subsequently change the state.

The ordering is: validate trustworthy header and mode; check AMO history; decode a new request; execute business logic; encode and save the result; drop or send the ordinary reply; attempt each eligible callback. History has no eviction during a server process lifetime. ALO bypasses duplicate suppression. Both modes use the same business implementation.

AMO is an at-most-once execution guarantee within the retained in-memory history, not an exactly-once or crash-recovery guarantee. Restart discards history. If attempts expire, the client reports that confirmation was not obtained and the execution result is unknown. It does not automatically switch to a new identity and repeat a reservation or fare increase. A separate query can inspect current state but is not a transaction receipt under concurrent clients.

## 5. Time-limited server callbacks

MONITOR registers a client for a flight for 1 to 3600 seconds. Multiple clients may monitor the same flight; monitoring one flight does not subscribe to another. Successful reservations create events containing flight ID, remaining seats and increasing update sequence. The dispatcher sends a 44-byte callback from the same server socket directly to each active subscriber. Callback identity is the original registration UUID/request ID, not the reservation identity.

An ordinary reply being lost or its send raising an I/O exception does not suppress the callbacks produced by that reservation. One callback recipient failing does not stop attempts to the others. The server checks subscription activity immediately before each send and periodically purges expired registrations during idle reception. AMO replay never emits a second copy of the business event.

A monitor confirmation is the sole dynamic replay exception. Immediately before initial or duplicate confirmation transmission, the dispatcher reads the original registration's remaining lifetime. It does not re-register or extend that subscription. If the registration expired or was replaced, remainingMillis is zero. ALO duplicates do re-execute registration, consistent with that mode.

The client begins its local monitoring deadline from a successful confirmation's remainingMillis. Duplicate confirmations do not renew it. Before confirmation, only the highest-sequence callback for the pending registration is retained; after confirmation, only strictly increasing sequences from the expected server and registration are shown. Gaps are allowed because callbacks have no acknowledgement or retransmission. The menu resumes when monitoring ends. These callbacks provide best-effort updates, not a reliable event stream.

## 8. Reproduction, conclusions and limitations

Build from the repository root using sh server/build.sh on macOS/Linux or server/build.ps1 on Windows. Start a new server to reset flights, subscriptions and history. Both client and server must select the same semantics.

```text
java -cp server/build/classes flight.ServerMain --bind 0.0.0.0 --port 6789 --semantics amo
python -X utf8 -m client --server <server IPv4> --port 6789 --semantics amo
```

For a controlled first-reply-loss run, restart the server with the selected mode and add --drop-first-reply 11111111-1111-4111-8111-111111111111:2. Start one new experiment process using the same mode and the fixed session. Its target mutation is request 2 after the initial query. For example:

```text
python -X utf8 -m client --server <server IPv4> --semantics amo
  --session-id 11111111-1111-4111-8111-111111111111
  --case reply_loss_reserve --flight-id 1001 --quantity 1
```

The displayed wrapped command should be entered on one shell line. Use reply_loss_increase with --delta 20 or reply_loss_set with --new-price 120 for the fare cases. Do not reuse the fixed identity across cases without restarting the server. On macOS/Linux, python3 may replace python. The --check option is offline and does not establish network connectivity.

For concurrent monitoring, B and C each register 1001 for 60 seconds, then a third client process on C's computer reserves one seat twice. For flight isolation, B registers 1001 and C registers 1002; the writer reserves one seat on each. Wait for registration confirmation before writing and keep the writes within both active intervals. Verify natural expiry and correlate server events with the original registration identities.

The observed system implements the six services, cross-language binary encoding, server callbacks, bounded retries and selectable invocation semantics. The six LAN fault runs support the expected ALO/AMO distinction for both non-idempotent writes and idempotent SET. Concurrent-client and expiry observations corroborate the functional design. Results are controlled observations, not delivery probability or throughput measurements.

State and request history are held in memory; restarting the server discards both. History has no eviction during a process lifetime. Callbacks are best effort with no acknowledgement/retransmission. The system has no authentication or crash-persistent transaction record and makes no exactly-once or production-reliability claim. The LAN isolation run is supported by both the client observations and A's original per-recipient server delivery records.
